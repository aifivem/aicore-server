# vRP bridge (ai-core)

ai-core presents itself as `vrp` (manifest `provide 'vrp'`, always started) and answers vRP 1.0, the vRP 0.5 call style, vRP 2 and vRP 3 at the same time, with no setting. Code: `resources/[ai]/ai-core/bridge/vrp/` (folder note `CLAUDE.md`), root files `lib/`, `cfg/`, `vRPShared.lua`, `client/vRP.lua`, JS side `resource/server/vrp/`.

Status: foundation, the vRP 1 API (server, client tunnel, 0.5 call style), the GUI (menus, prompt, request, notifications on ai-lib), the panel tab for `data/vrp.json` and vRP 2 / 3 extensions are written; type checked, linted, built, Lua language server 0 diagnostics. On the dev server the include chain is confirmed server side with the W0 probe (`resources/[test-vrp]/vrp-probe`, not in git): `GetResourceState('vrp')` started, `LoadResourceFile('vrp', ...)`, `module("vrp", ...)`, a synchronous proxy answer outside a thread, and again after `tools/restart.ts`. Client side and the API calls are not yet run with a player; no real vRP script has been run yet.

## Works now

- `shared_script '@vrp/lib/utils.lua'` resolves to ai-core's `lib/utils.lua` (globals `SERVER`, `CLIENT`, `module`, `async`, `class`, `parseInt`, `parseDouble`, `parseFloat`, `sanitizeString`, `splitString`, `joinStrings`, `tohex`, `clone`, `formatNumber`, `table.maxn`).
- `module("vrp", "lib/Proxy" | "lib/Tunnel" | "lib/Tools" | "lib/IDManager" | "lib/Luaoop" | "lib/htmlEntities" | "lib/Luang" | "lib/Lang" | "lib/Debug" | "cfg/base" | "cfg/modules" | "cfg/client" | "cfg/gui" | "cfg/lang/en" | "vRPShared" | "client/vRP")`, on both sides (every file is in ai-core's `files`). `LoadResourceFile("vrp", ...)` resolves to ai-core through the provide (engine source: `GetResource(name, withProvides = true)`).
- Proxy and Tunnel keep vRP's event names and argument order, so scripts that ship their own copy talk to ai-core. A proxy answer that does not wait comes back synchronously (also outside a thread).
- vRP 0.5 calls: `vRP.getUserId({source})`, `vRP.getUData({id, key, function(v) end})`, `vRP.prompt({player, title, "", function(player, text) end})`, `vRPclient.getPosition(src, {}, function(x, y, z) end)`.
- `vRP.getUserId(source)` (= ai-core character id, nil on the character screen), `getUserSource(user_id)`, `getUsers()`.
- Events `vRP:playerJoin (user_id, source, name, "")` when the character loads, `vRP:playerSpawn (user_id, source, first_spawn)` 2 s after ai-core spawns it, `vRP:playerLeave (user_id, source)` on drop or character switch.
- Client `vRPclient.getPosition(source)` and client proxy `vRP.getPosition()`.

## vRP 2 / 3 extensions

Samples checked by reading: vRP-basic-mission, trew_hud_ui (VRP2), the 11 foxoak vrp2_scripts extensions.

- `local vRP = Proxy.getInterface("vRP"); async(function() vRP.loadScript("<res>", "<path>") end)` on the server or the client runs `<res>/<path>.lua` inside ai-core's Lua runtime, once per file. Each file gets its own globals (over ai-core's), so a script's globals never touch ai-core or another script; `vRP`, `class`, `module`, `async`, `Proxy`, `Tunnel`, `SERVER` / `CLIENT` and the natives are there. Its event handlers, net events, threads, timeouts, commands, NUI callbacks, interfaces, extensions, User methods, menu builders, permission functions, items and prepared queries belong to it: when its resource (or the one that loaded it) stops they are removed, its threads end at their next `Wait`, its commands do nothing, and the next `loadScript` loads the file again. A compile or runtime error prints one line with the file and leaves ai-core running; every listener, interface function and callback runs protected.
- `vRP`: `EXT`, `Extension`, `registerExtension`, v3 `unregisterExtension`, `triggerEvent`, `triggerEventSync`, `log`, `error`, `cfg`, `lang`, `modules`, `users` (account id -> user), `users_by_source`, `users_by_cid`, `prepare` / `query` / `execute` / `scalar` (ai-core's pool, `@name` params), `get/setUData` (account), `get/setCData` (character), `get/setSData(key, value, id)` (server id, `''` when nil, shared with vRP 1's SData), `get/setGData`, `kick`, `save`, `getPlayerName`, `registerDBDriver` (ignored).
- `class("X", vRP.Extension)`: `.tunnel` / `.proxy` answer as "vRP.EXT.X" (a script's own client vRP talks to it), `.remote` reaches the client side, `.event` listeners run in their own threads, `.User` methods reach every user, also users who joined before the extension loaded (its `User.__construct` runs for them).
- `User`: `id` (ai-core account id), `cid` (character id), `source`, `name`, `spawns`, `data` (per account) and `cdata` (per character; extensions' own keys are stored in ai-core's vRP data table, `wallet` / `bank` / `groups` / `inventory` / `vitals` read ai-core's data, writing `wallet` / `bank` changes the money), `identity`, `isReady`, `save`; money `getWallet`, `getBank`, `setWallet`, `setBank`, `giveWallet`, `giveBank`, `tryPayment`, `tryWithdraw`, `tryDeposit`, `tryFullPayment`, v3 `tryCardPayment` (with `dry`, booleans); groups `hasGroup`, `getGroups`, `addGroup`, `removeGroup`, `getGroupByType`, `hasPermission`, `hasPermissions` (the panel's vRP mapping, as vRP 1); inventory `getInventory`, `tryGiveItem`, `tryTakeItem`, `getItemAmount`, `getInventoryWeight`, `getInventoryMaxWeight`, `clearInventory`, `openChest` (the inventory layer and the panel's `items` mapping); survival `getVital` / `setVital` / `varyVital` (`food` / `water` = ai-hud's hunger / thirst on vRP's 0-1 scale); menus `openMenu`, `closeMenu`, `actualizeMenu`, `closeMenus`, `getMenu`, `prompt`, `request` (ai-lib's menu and dialogs); areas `setArea`, `removeArea`, `inArea`; missions `startMission`, `nextMissionStep`, `stopMission`, `hasMission` (a GPS route and a notification per step).
- Core extensions: `Base`, `Survival`, `PlayerState`, `Map`, `GUI`, `Identity`, `Group`, `Money`, `Inventory`, `Mission`. `vRP.EXT.<core>.remote` is the vRP client tunnel (the functions of `vRPclient.*`, plus v3 `getHeading`, `notifyHelp`, `clearHelp`); `Group:getUsersByGroup` / `getUsersByPermission` / `getGroupTitle` / `registerPermissionFunction`, `Money:formatWallet`, `Inventory:defineItem` (its `menu_builder` opens when the item is used) / `computeItem` / `computeItemsWeight` / `parseItem`, `Identity:getIdentity(cid)` (also stored characters; `name` and `lastname`) / `getByRegistration` / `getByPhone`, `Survival:registerVital`, `GUI:registerMenuBuilder` / `buildMenu`. On the client the core extensions call the vRP 1 client functions (`vRP.EXT.Base:notify(text)`).
- Events: `characterLoad` (sync) when ai-core loads a character, then `playerJoin` for the first one of a connection; `characterUnload` (sync) on a switch or drop; `playerLeave(user, reason)` (sync) on drop; `playerSpawn(user, first_spawn)` 2 s after ai-core spawns the character (first = first of the connection); `playerDeath`; `playerMoneyUpdate`; `playerJoinGroup` / `playerLeaveGroup`; `playerVitalChange` / `playerVitalOverflow`; `playerMissionStart` / `playerMissionStep` / `playerMissionStop`; `save` every 60 s; `extensionLoad`; v3 `extension-Unload`. Client: `playerSpawn`, `playerDeath`, `playerTeleport`.

## Known limits

- `vrp` always reads `started` (owner decision): multi-framework scripts that check vrp first take their vRP path.
- Creative v5 (PascalCase API, `@vrp/lib/Utils.lua`, `@vrp/config/*.lua`) is not answered (owner decision); Creative v3 / v4 lowercase extras come after the core.
- Direct SQL on vRP's own tables (`vrp_users`, `vrp_user_identities`, `vrp_user_data`, `vrp_srv_data`, ...) finds nothing (owner decision).
- A real `vrp` resource or a vRP DB driver (`vrp_mysql`, `vrp_oxmysql`, `vrp_ghmattimysql`, `vRP-db-drivers`) must be deleted: ai-core's connection gate names them.
- `vRP:playerSpawn` fires for the first spawn of a character load only; respawns after death come from the death script, not as vRP spawns. `last_login` of `vRP:playerJoin` is empty.
- The old include `@vrp/client/Proxy.lua` (vRP 0.x) is not shipped. vRP's NUI, voice, profiler and `vRP:reload` (v3) are not answered.
- Multi-statement queries take named (`@name`) params; positional `?` values are given to every statement.
- GUI: menus have no left / right (`mod` is always 0, so vRP 2 options that step a value with the arrow keys only take the plain pick); a pick hides the menu until the choice ran, then it shows again unless the choice opened, changed or closed one; a request takes the mouse like any dialog (vRP's F5 / F6 overlay is not copied) and a closed request answers no; Escape goes back one menu, holding it closes every menu; menu, prompt and request texts are cut to ai-lib's lengths (title 60, row 80, description 160 characters; longer prompt titles move into the field label, longer requests into the row descriptions).
- v1 limits: `giveInventoryItem` / `tryGetInventoryItem` show no vRP notification text (the `notify` argument is ignored); `wammo|...` ids need a panel `items` row; `getInventoryMaxWeight` answers 100000 kg when the active inventory has no weight export (the inventory still refuses a full pocket); `openChest` callbacks (`cb_close`, `cb_in`, `cb_out`) are not called; `getUserByRegistration` / `getUserByPhone` find loaded characters only; hunger / thirst overflow damage is ai-hud's (not copied); `setHandcuffed` / `toggleHandcuff` and `killComa` do nothing (the police / death script owns them); a client script cannot give weapons (`vRP.giveWeapons` on the client warns), its `getWeapons` reads the held weapon only; a script that ships its own `Tunnel.lua` sends `giveWeapons` to the client, where it is refused; `getUserDataTable` writes go nowhere; Zirix's wallet item (`dinheiro`) is the `cash` account only through `getMoney` / `giveDinheirama`.
- vRP 2 / 3: `vRP:reload` and `cfg.moduals` (v3: any client could restart resources) are not answered; neither are v3 `screenFade` / `teleportFade` and the v3 core modules `weather`, `commands`, `misc`, `weapon`, `log`. Modules not answered: Phone, Garage, Home, Business, Aptitude, Police, Shop, Transformer, Audio, Radio, ATM, Edible (`vRP.EXT.Phone` and the like are nil). `Map.remote` entities (`addEntity`, `setEntity`, `commandEntity`) and `GUI.remote` divs answer what the vRP 1 client answers; the menu `select` event never fires. `Inventory:loadChest` / `unloadChest` and `openChest`'s move callbacks are not answered. `createCharacter` / `deleteCharacter` answer nil / false, `useCharacter(other id)` opens ai-core's character screen, `getCharacters` lists the loaded character only; `playerRejoin`, `playerDelay`, `playerStateLoaded`, `characterIdentityUpdate` are not fired; `endpoint` is `0.0.0.0`; `Identity:getByRegistration` / `getByPhone` find loaded characters only. Queries of vRP's own core (`vRP/...` names on vRP's tables) do not exist. Extension tunnels are not rate gated (vRP's own design: each script validates its arguments). A loaded extension runs in ai-core's runtime: its CPU time shows under ai-core in resmon, and natives it calls directly that register something not listed above (exports, key mappings) are not undone when it stops.

## Panel data

`data/vrp.json` (ai-core panel file `vrp`, server only): `defaults` (built-in rules `<job>.*` on duty, `admin.*`, `player.*`), `permissions` (permission or `prefix*` -> job + grade + on duty, gang + grade, extra group, admin, everyone), `groups` (vRP group name -> job / gang grade or admin), `items` (vRP item id -> inventory item), `seen` (every permission string scripts asked for, written by ai-core).

Edited in ai-core's panel, tab "vRP scripts" (`VRP_TAB` in `resource/server/vrp/schema.ts`), one card per section: built-in rules (switches), permission rules (permission name, "who has it" = a job + lowest grade + only on duty, a gang + lowest grade, a group, admins or everyone; the row's `who` keeps only that target, a row without `who` (hand edit) counts every filled target), group names (group name, "means" = a job grade, a gang grade or admin), item names (with the item picker), asked permissions (searchable, 50 at a time, "Add rule" puts a rule for that name at the top of the rules, admins only until the owner picks who). Jobs, gangs, grades and items are pickers; the server refuses a new or changed row whose grade the job or gang does not have ("lower the grade first"); a row with an empty name or target does nothing (and a rule that names a permission switches the built-in rules off for it).
