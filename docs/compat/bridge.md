# ESX / QB / Qbox bridge (ai-core)

ai-core presents itself as `es_extended`, `qb-core` and `qbx_core` (manifest `provide`) and answers their exports, core objects and events from Lua in `resources/[ai]/ai-core/bridge/`. Every call goes to ai-core; the player mirror follows ai-core's local events. Status: written and checked on the dev server with a test resource after a full server restart (resource states, exports, legacy events, Shared tables, item definitions; the three framework file includes from a resource that includes them like an ESX / QB script); not yet tested with a real ESX / QB script. Prepared for that test: esx_joblisting 1.14.1 (ESX-Legacy-Addons, needs only es_extended) and qb-cityhall (its server part needs only qb-core), cloned under `ai-core-research/bridgetest` and `ai-core-research/jobs`; running downloaded third-party code on the dev server needs the owner's go-ahead, so it was not started.

vRP (1.0, 0.5 call style, 2, 3) is answered too (`provide 'vrp'`, `bridge/vrp/`): its coverage and limits are in `docs/compat/vrp.md`.

## Shared data and vehicle properties

- Vehicles and weapons for every framework view come from ai-core's copies of qbx_core's `shared/vehicles.lua` / `weapons.lua` (`BridgeShapes.sharedData`): `QBCore.Shared.Vehicles` (by model, with `spawncode`, `shop` default `pdm`) / `VehicleHashes` / `Weapons`, Qbox `GetVehiclesByName/Hash/Category` / `GetWeapons`, ESX `GetVehicleType`. ESX's own weapon table (labels, components, tints) is `bridge/esx/weapons.lua`, generated from es_extended's config with English labels.
- Vehicle properties (`ESX.Game.Get/SetVehicleProperties`, `QBCore.Functions.Get/SetVehicleProperties`, Qbox `qbx_core:client:setVehicleProperties`, the ESX `VehicleProperties` bag) use ox_lib's code in `bridge/core/vehicleprops.lua` (ox / ESX / QB shape; QB extras come back as 0 = on, 1 = off). ai-core's own `ai:props` bag keeps its `v: 1` shape.
- QB job / gang shapes are `BridgeShapes.qbJobDefinition` / `qbGangDefinition` on both sides; Qbox's (integer grade keys, `bankAuth`) are `BridgeQbox` (`bridge/qbx/shared.lua`). QB's Shared helpers and tables load on both sides from `bridge/qb/shared.lua`. Buckets, opt-in, offline players, `SetField` and the generated ids (citizenid, fingerprint, wallet, account, phone, serial) have one implementation in the QB bridge that the Qbox exports call.

## Framework UI (client)

ESX's and QB's UI is drawn by ai-core's own menu, input dialog, prompts, notifications and progress bar (`bridge/core/ui.lua`); no framework NUI runs. ai-core `provide`s `esx_context`, `esx_textui`, `esx_notify`, `esx_progressbar`, `esx_menu_default`, `esx_menu_dialog`, `esx_menu_list`, `qb-menu`, `qb-input` and `progressbar` and answers their exports, so those resources must not be installed (the connection gate names them for deletion). The framework menus stack (a sub menu over its parent) while ai-core shows one dialog at a time: the bridge keeps the stack, shows its top, and shows a menu again when it stays open after a pick (esx_context and ESX default menus stay open until the script closes them). Closing from code uses ai-core's client export `CloseDialog()`.

## Known limits

- One job per framework view: ai-core's current job (on duty, else last on duty, else the first). Qbox's primary job is that job, so `SetPlayerPrimaryJob` puts the player on duty.
- Offline players (QB `GetOfflinePlayer*`, Qbox `GetOfflinePlayer` / `CreatePlayer`) carry the character's identity only: money, jobs, gangs and metadata are empty and their money / job functions answer false; changes on them are not saved. `GetOfflinePlayerByLicense` finds nobody; `GetGroupMembers` and `SearchPlayers` cover loaded characters only.
- Characters, jobs and bans live in ai-core: `Login`, `DeleteCharacter`, job / gang / grade create / upsert / remove (`CreateJob`, `Upsert*`, ESX `CreateJob`) answer the framework's failure shape; `IsPlayerBanned` is false, `IsWhitelisted` true, `ExploitBan` drops and logs without storing a ban.
- Script-added QB Shared jobs / gangs / items show in `QBCore.Shared` but are not ai-core jobs: `SetJob` to one fails; panel jobs and inventory items cannot be changed that way.
- Session only: QB / Qbox `SetPlayerData` with a custom key, `SetCharInfo`, `SetCreditCard`, `AddField`, `SetField`, permissions given with `AddPermission`; ESX `togglePaycheck` (ai-core's paycheck ignores it), `setGroup` (admins are the `ai.admin` ace).
- Weapons and weight: ESX weapon ammo, component and tint changes, `setMaxWeight` and QB `SetInventory` answer false (the bridge cannot change item metadata or a weight limit); `esx:updateWeaponAmmo`, ESX pickups and client `esx:addWeapon` / `removeWeapon` / `setWeaponAmmo` are not answered.
- Vehicles: a client cannot create networked entities (`sv_entityLockdown`): `ESX.Game.SpawnVehicle` makes a local vehicle (networked ones come from `ESX.OneSync.SpawnVehicle`), QB's client `SpawnVehicle` asks the server (admins) and falls back to a local one; `AttachProp` props are local. Qbox vehicle persistence only sets the `persisted` flag. `GetVehicleClass` needs one loaded player.
- Snapshots: QB `PlayerData.items` up to 1 s old; ESX xPlayer `inventory` / `loadout` / `weight` refresh when their getter runs; client ESX `PlayerData.inventory` fills only from the server or the inventory; `esx:enteringVehicle` fires with `enteredVehicle`, `enteringVehicleAborted` never.
- Buckets picked by scripts share numbers with ai-core's allocator (1000 and up): the bridge warns once per resource.
- Qbox hooks run for money changed through the Qbox exports and the player object only.
- ESX has no nationality field; ai-core's `nationality` reaches only QB / Qbox `charinfo`.
- Exports a server added to its own modified framework copy are not answered (`exports.qbx_core:GetPoliceJobs()` is not in Qbox): a config that calls one errors at load and leaves the rest of that config unset (`langs`, `locations` nil); write the value itself (`{ "police" }`). A real `qbx_core` / `es_extended` / `qb-core` folder next to ai-core does not bring them back: the connection gate names it for deletion.
- UI limits: ai-core's menu shows 40 rows (longer ESX / QB menus are cut); ai-core has no unfocused menu, so `ESX.PreviewContext`, esx_context `focusPreview` and qb-menu `showHeader` show nothing; an ESX interaction fires only while an ESX text UI or help prompt is on screen (ESX runs them on any press of its key); text fields must not be empty to confirm (optional qb-input fields too); qb-input `checkbox` fields are not asked; QB progress props are not attached.
- Not tested with the server running yet (written while the dev server was down): every addition above passed the Lua language server only.
