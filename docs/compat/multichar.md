# Character screens (multichar scripts)

ai-core has its own character screen (built in, it cannot be removed). When a server installs another character screen, ai-core switches its own off by itself and lets that script log players in; the script runs unchanged. Code: `resources/[ai]/ai-core/resource/server/multichar/` (folder `CLAUDE.md`), client `resource/client/multichar.ts`.

## Detection and the panel

- Registry `multichar/registry.ts`, picked by `AdapterPicker` like every layer: once at start and again when a listed script starts or stops. Panel: General, Character screen: `characterScreen` = `auto` (default: the first running script of the list, else ai-core) / `ai-core` / a script's name (when it does not run, ai-core's screen stays on so players can always join); a read-only row shows the screen in use (`characterScreenActive`).
- The console prints `characterScreenChanged: <script> shows the character screen; ai-core's own screen, its bucket and its spawn are off` (or `... ai-core's own character screen is on`) on every switch.
- GlobalState `ai:characterScreen` (`CORE.characterScreenKey`) holds the external script's name; export `GetCharacterScreen()` answers `"ai-core"` or that name.
- While an external screen runs ai-core does not open its screen (client boot and `ai-core:characters` refuse), does not put the joining player into its private bucket, and runs neither its spawn nor its spawn chooser. The joining player's account is upserted at `playerJoining` (so the login exports find it). When the external script stops, players without a character get ai-core's screen at once; when one starts, ai-core's open screen closes and its bucket is given back.

## Login entry points (server exports, `MulticharServerExports` in `@aicore-fivem/shared`)

| Export | Does |
|---|---|
| `GetCharacterScreen(): string` | `"ai-core"` or the external screen's resource |
| `LoginCharacter(source, character, done?)` | loads a character of the player's own account; `character` = char id, `{ slot }` (ESX `char<slot>`) or `{ citizenid }` (QB / Qbox); another account's character answers `CHAR_ERR_GONE` |
| `CreateAndLoginCharacter(source, { firstname, lastname, birthdate, sex, nationality?, slot? }, done?)` | checked like the create form (`toName`, `toBirthdate` YYYY-MM-DD 18-100, `"male"` / `"female"`, nationality empty when left out), slot limit of the account, `slot` left out = first free one; then loads it |
| `LogoutCharacter(source, done?)` | saves and unloads (`playerUnloaded` "switch"); the external screen gets `CORE.externalLogoutEvent` on the client and shows itself again (under ai-core's screen: ai-core's screen opens). `CHAR_ERR_NOT_LOADED` without a character |

`done(result)` gets `{ ok: true }` or `{ ok: false, error: "CHAR_ERR_*" }` once; nothing crosses as a promise (Lua: a `promise` + `Citizen.Await` around the callback). A login waits for the account upsert of a player who just joined.

## Spawn under an external screen

The script places, models and dresses the ped (and runs its own spawn selector). ai-core loads the character the same way as for its own screen (snapshot to the client, `playerLoaded` right away), but sends `CORE.externalLoadedEvent (armour, health)` instead of `ai-core:client:spawn`: no teleport, no model change, no bucket move. The client waits until the player stands in the world (screen faded in, no NUI focus, ped visible, no player switch, three checks 500 ms apart), then puts the saved armour and health on the ped, fires `client:playerLoaded`, and reports `CORE.externalSpawnedEvent`; the server then fires `playerSpawned` (once per load, only for the character it waits for). A player who sits in the script's spawn selector is spawned when it closes.

## Framework tables (`players`, `users`, `jobs`, `job_grades`)

Multichars read characters with raw SQL from the framework's tables, so ai-core writes projections of its own data under those names while an external screen runs (panel `frameworkTables`: `auto` = with an external screen, and during the first minute of a boot while a listed script is installed, since esx_multicharacter alters `users` when it starts; `on`; `off`).

- Ownership: each table's COMMENT starts with `ai-core projection`. A table of that name without the mark (a server moved from QB / ESX keeps its real ones) is never created over, written or dropped: the console warns, and the script reads what is in it. Turning on drops ai-core's marked tables and creates them fresh (schema always current, no stale rows after a crash); turning off drops them (`DROP TABLE` takes their triggers along).
- `players` (QB / Qbox): `citizenid` (primary key), `cid` = slot, `license` = `license:<hash>`, `name` (FiveM name), JSON `money` (every ai-core account by name), `charinfo` (firstname, lastname, birthdate, gender 0 / 1, nationality, cid), `job` (QB shape with label, payment, isboss, onduty, grade name / level of the current job), `gang` (active gang, else `none`), `position` ({x, y, z, heading}; the default spawn for a new character), `metadata`; plus ai-core's `id` (character id) and `user_id` (account). Keys: `citizenid`, unique `id`, `user_id`, `license`.
- `users` (ESX): `identifier` = `char<slot>:<license without prefix>` (primary key), JSON `accounts` (`cash` as `money`, `bank`, `black_money`, others by name), `job` / `job_grade` (current job; a job that is no longer defined shows as unemployed), `firstname`, `lastname`, `dateofbirth` (YYYY-MM-DD), `sex` (`m` / `f`), `height` (metadata `height`, else 0), `position`, `metadata`, `group` `user`, `disabled` 0, `skin` NULL, `last_seen`; plus `id` and `user_id`.
- `jobs` (`name`, `label`, `whitelisted` = not listed in job centers) and `job_grades` (`job_name`, `grade`, `name` = label lower case with `_`, `label`, `salary`): every panel job, the unemployed one included (tgiann-multichar reads `jobs.label` of every character's job).
- Rows exist only for connected accounts: built when the player joins (before the multichar reads), rebuilt on load, unload ("switch"), create, delete, and for accounts whose QB rows carry a job or gang edited in the panel; removed when the player leaves. Not on money, duty or metadata changes: a row shows the state at the last of those points (an unload writes the final state, read from memory before the save lands). 100k or 1M stored accounts cost nothing; the tables stay at online accounts x slots.
- Writes: one transaction per batch of up to 100 accounts (`DELETE ... WHERE user_id IN (?)` + multi-row `INSERT`, 500 rows per statement), all projection work serialized in one chain; reads are four indexed queries per batch (characters by `user_id`, accounts by `owner_type, owner_id`, jobs and active gangs by `char_id`).
- Deletes reach ai-core: an `AFTER DELETE` trigger on `players` and `users` soft-deletes the character (`UPDATE ai_core_characters SET deleted_at = NOW() WHERE id = OLD.id AND deleted_at IS NULL`, one primary key update per row) unless the session variable `@ai_core_projection` is set, which only ai-core's own refresh does on its own pool connection. A trigger is cheaper and more exact than any watcher (no polling, works inside the script's own transaction). Without the TRIGGER privilege (or with binary logging that refuses triggers) the console warns and such deletes stay in the table only. The trigger also notes the character in `ai_core_deleted_log` (only one it really soft-deleted); the account's next projection refresh (the player loads or creates a character, or leaves) reads its rows by index, removes them and fires `characterDeleted` for each (the `GetCharacterInfo` cache drops it); enabling or disabling the tables reads the whole log once. No timer reads it.
- Inserts and updates by other scripts are ignored: the next refresh of that account rewrites its rows (esx_multicharacter's `disabled` slots, 0r's renumbering of ESX identifiers after a delete). `TRUNCATE` fires no trigger.
- Checked on MariaDB 11.4.7 against the shipped `ddl.ts` (scratch database): trigger creation, ai-core's own deletes keep characters, a third-party transaction delete through `players` and through `users` soft-deletes, a real `jobs` table is reported foreign and survives, the reads of tgiann-multichar (ESX `LIKE '%<license>'` and QB), qb-multicharacter (`SELECT * ... WHERE license = ?`) and esx_multicharacter (`identifier IN (...)`) answer, the job-holders `JSON_EXTRACT` query, `TRUNCATE` fires nothing, `DROP` leaves no trigger. With 100k characters and 10k projection rows: one account's rebuild (3 rows, own transaction) 1.6 ms, a third-party delete of 3 rows with the trigger 1.1 ms, the QB read uses `license`, the refresh delete uses `user_id`. Portable SQL only (no TEXT defaults, `JSON_UNQUOTE(JSON_EXTRACT())` instead of `->>`, the trigger body without `BEGIN`).

## What the bridge does

- QB `QBCore.Player.Login(source, citizenid | false, newData)` and Qbox `Login`: `LoginCharacter(source, { citizenid })`, or `CreateAndLoginCharacter` from `newData.charinfo` (gender 0 / 1 / Female, birthdate to ISO, `cid` = slot, `height` kept in metadata); another account's citizenid answers false. `Logout` (QB, Qbox, Player) calls `LogoutCharacter`. `DeleteCharacter` checks the account (another account's citizenid drops the player, as qb-core does) and calls `DeleteCharacter`; `ForceDeleteCharacter` drops a loaded player first.
- ESX `esx:onPlayerJoined (source, 'char<N>' | 'char<N>:<license>', data?)` (server-raised only, the license must be the player's own): with `data` a new character in slot N, else the slot N character. `esx:playerLogout (source, cb)` calls `LogoutCharacter`.
- ESX identifiers: `xPlayer.identifier` stays the citizen id whichever screen runs (data ESX scripts stored stays valid); `GetPlayerFromIdentifier` / `GetPlayerIdFromIdentifier` also take `char<N>:<license>`; `ESX.GetIdentifier` is the license without prefix; `ESX.Players` is writable.
- Loaded events under an external screen: the client mirror loads on `ai-core:client:externalLoaded`; QB `OnPlayerLoaded` / `isLoggedIn` are left to the multichar or qb-spawn (set on their `OnPlayerLoaded`, or once the player stands in the world); `esx:playerLoaded` fires on the client at login (never also sent from the server); `esx:onPlayerSpawn` is left to the screen.

## Limits

- A multichar whose spawn flow never fades the screen in or keeps NUI focus delays `client:playerLoaded` / `playerSpawned` until it does.
- Rows show money, job and metadata as of the last refresh point (join, load, unload); scripts reading them while a character plays see that snapshot.
- ESX `dateofbirth` is ISO (YYYY-MM-DD), not esx_identity's display format; `users.skin` is empty (looks come from ai-core's appearance layer, the multichar's own clothing integration shows the preview).
- A delete through the tables fires `characterDeleted` only at that account's next projection refresh (above), not at once. Accounts without a stored license have no rows.

A new multichar: one line in `MULTICHARS` (resource, tested version), a row here with what it reads and calls.
