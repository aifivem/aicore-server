# Lua (ai-core's bridge, ai-lib's Lua side)

The Lua in the project is ai-core's framework bridge (`resources/[ai]/ai-core/bridge/{core,qb,qbx,esx}/{server,client}.lua`, plus `modules/playerdata.lua` for Qbox includes), loaded after ai-core's JS in the same resource through `fxServerScripts` / `fxClientScripts` in `package.json`, and ai-lib's Lua side (`resources/[ai]/ai-lib/init.lua` + `lua/{shared,client,server}/<name>.lua`, one module per `aiLib.<name>`, loaded on first use in the calling resource). Everything else is TypeScript. Coverage: `docs/compat/bridge.md`.
- ai-lib's Lua side mirrors the TypeScript lib: same names where Lua allows (`aiLib.notify`, `aiLib.Points.new()`, `aiLib.addCommand`), the same wire formats (callbacks `aicore:cb:<name>` / `aicore:cbr:<resource>`, keybind and prompt events, state bag keys), so Lua and TypeScript resources work together. A lib change that a Lua user can see is made on both sides; every module carries LuaLS annotations and its field in `init.lua`'s `AiLib` class; check with the Lua language server (0 diagnostics).
- A server native whose player parameter is `char*` (`IsPlayerAceAllowed`) gets `tostring(source)`: a Lua number 0 (the console) goes to native code as a null pointer ("Argument at index 0 was null").
- Lua 5.4 (CfxLua); no `lua54` line in the manifest (Lua 5.3 was removed in June 2025).
- Every function, table and field a ready-made script can touch has LuaLS annotations (`---@class`, `---@field`, `---@param`, `---@return`) matching the original framework's documented types.
- ai-core `provide`s `es_extended`, `qb-core` and `qbx_core` (manifest, always on: a provided name reports `started` whether or not the bridge answers). `provide` does not alias exports: the bridge answers `exports['qb-core']:X()` through `__cfx_export_qb-core_X` handlers, the same way ai-mysql answers oxmysql.
- The bridge holds no game logic: every call forwards to ai-core (same resource, JS side) and the `xPlayer` / `PlayerData` mirrors update from ai-core's local delta events, never by calling ai-core per read.
- A table handed to another resource (core object, Player, xPlayer) is copied by msgpack: metatables and `__index` proxies are lost, functions become references back into ai-core. Hand out plain tables filled at that moment (`QBCore.Shared.*` is rebuilt on every `GetCoreObject`).
- `provide` lines added while the server runs report `missing` in `GetResourceState` (even after `refresh` and a resource restart) until the next full server start; exports and events answer at once.
- Check the bridge with the Lua language server and fix every diagnostic: `qbx-lua-ls.exe --check .` in `resources/[ai]/ai-core` (the exe ships in the VS Code "Qbox Lua" extension, `server/win32-x64/`); LuaLS sees `ESX` as either `ESXClient` or `ESXServer`, so a field one side's files use is declared on both classes.
- A function another resource hands to the bridge (callbacks, `onSelect`, menu `submit`) arrives as a callable table (msgpack function reference), never `type(fn) == 'function'`: test it with `BridgeUI.isCallable` and call it through `BridgeUI.call` (pcall, the bridge's menu state survives a script error).
- Framework UI (ESX context / menus / text UI / progress, qb-menu, qb-input, DrawText) goes through `bridge/core/ui.lua` onto ai-lib's menu, input, prompts and progress bar (exports `exports['ai-lib']`, events `ai-lib:client:*`); never a NUI of the bridge's own. Framework UI resources ai-core answers are `provide`d and listed in `connection/conflicts.ts` `NEVER_NEXT_TO`.
- No ox_lib dependency in the bridges: the bridge runs on ai-lib's Lua side (`aiLib.*`) from ai-core's copy in `bridge/lib/` (ai-lib starts after ai-core, so it cannot be included; the copy is refreshed from `resources/[ai]/ai-lib` on every ai-core build by `scripts/postBuild.ts`, never edited). A bridge function whose job a lib helper does (notify, admin check, rate gate, loaders, zones, keybinds, commands, progress, waits, location and vehicle names, number helpers) calls the helper and only maps the framework's arguments and return shape; a helper the bridge needs that the lib lacks is added to the lib (TS + Lua) first. The scripts the bridges serve may load ox_lib themselves.
- The bridge holds no second copy of ai-core's player data: the server mirror follows ai-core's local events (`playerLoaded`, `moneyChanged`, `jobsChanged`, `dutyChanged`, `gangsChanged`, `activeGangChanged`, `metaChanged`, `definitionsChanged`) and keeps O(1) indexes (citizenid -> source, job -> on-duty sources); the client mirror reads ai-core's own player data channel (`ai-core:client:playerData` / `playerDataPatch`, `ai-core:client:playerLoaded`) and the job / gang definitions from ai-core's client (`GetDefinitions` + `CORE.clientDefinitionsEvent`). The framework's job is ai-core's current job (`GetCurrentJob`, `AiPlayerData.job`), never picked again in Lua.
- Shapes both sides hand out (QB / ESX job tables, Qbox's group match) live once in `bridge/core/shapes.lua` (`BridgeShapes`), loaded on both sides.
- Same security and sync rules as the TS code: validate client input, snapshot + delta, no polling.
- vRP (`bridge/vrp/`, folder note `bridge/vrp/CLAUDE.md`): ai-core also `provide`s `vrp`; the `@vrp/...` files live at ai-core's root (`lib/`, `cfg/`, `vRPShared.lua`, `client/vRP.lua`, all in `fxFiles`). Keep vRP's Proxy / Tunnel event names and argument order; v1 functions go on `BridgeVRP.proxy` / `BridgeVRPClient.tvRP`, client-callable server functions on `BridgeVRP.tunnel` (rate gated). Copied vRP files stay unchanged (header + `---@diagnostic disable` only).
- One behaviour, one implementation across the framework views: what QB and Qbox both answer (buckets, opt-in, offline players, `SetField`, generated ids) lives in the QB bridge and the Qbox export calls it; shapes both sides hand out live in `BridgeShapes`; QB's Shared helpers load on both sides from `bridge/qb/shared.lua`. A new framework function first looks for the same job in ai-lib (`aiLib.*`), ai-core's exports and the other framework files.
- Framework files scripts include or `require` (`@qbx_core/modules/lib.lua`, `hooks`, `logger`, `shared/vehicles.lua` / `weapons.lua`) are copied unchanged at the same path in ai-core (header + `---@diagnostic disable` only) and refreshed from upstream, never edited; a copied file that redefines a native global (qbx `modules/utils.lua`'s `DeleteVehicle`) is not shipped.
- ai-lib's Lua callback ids start at `1 << 40`: a resource that bundles the TS lib and the Lua side (ai-core) hears both sides' answers on one `aicore:cbr:<resource>` event, and equal ids take each other's answers.
- Coverage and limits of every framework function: `docs/compat/bridge.md`; a function that cannot be real still exists with the framework's return shape and a listed limit, never nil, never a faked money or item success.
- ai-core exports that own entries by `caller()` (runtime job / gang definitions) see ai-core when the bridge calls them: the bridge keeps which script asked (`Bridge.putDefinition` / `dropDefinition`) and drops that script's entries on its `onResourceStop`.
- Under an external character screen (`docs/compat/multichar.md`) the client mirror loads on `ai-core:client:externalLoaded` and the bridge's `'spawned'` change follows on `client:playerLoaded`; framework "loaded" events the screen fires itself are not fired a second time.

## Files and folders (Lua)

The same standard as the TypeScript (`resource-structure.md` "Files and folders"), shaped by how FiveM loads Lua: files run in manifest order (`fxServerScripts` / `fxClientScripts` in ai-core's `package.json`) and share one global scope per side, without `require`. `bun tools/structure.ts` checks it.

- One folder per framework and side: `bridge/<framework>/server/`, `client/`, `shared/` (`bridge/esx/server/xplayer.lua`, `bridge/qb/client/functions.lua`); `bridge/core/` for what every framework view uses. One concept per file, named by what it holds (`callbacks.lua`, `items.lua`, `offline.lua`); never `utils`, `helpers`, `misc`, `functions` (a framework's own API name is fine: `QBCore.Functions` lives in `functions/`), about 200 lines at most.
- Everything a file keeps for itself is `local`; it shares through its framework's namespace table. Each global table is created in exactly one file (`BridgeQB = {}` in the framework's first file) and other files add fields to it (`function BridgeQB.offline(...)`); the framework globals scripts expect (`ESX`, `QBCore`, `QBX`, `vRP`) are created once the same way. No other globals.
- Load order is the dependency order: a file only uses what earlier files (in `package.json`) created; a new file gets its line there in the right place, never at the end by habit.
- Data tables (weapon lists) live in a `data/` folder next to their framework (`bridge/esx/data/weapons.lua`) and are read with `LoadResourceFile`; the checker skips `data/`.
- Files at a path another framework fixes (`@es_extended/imports.lua`, `@es_extended/locale.lua`, `@qb-core/shared/locale.lua`, `@qbx_core/modules/*`, `@qbx_core/shared/*`, `@vrp/lib/*`, `@vrp/cfg/*`, `vRPShared.lua`, `client/vRP.lua`, ai-mysql `lib/MySQL.lua`) keep their path and name; copied third-party files stay unchanged. The checker looks at `bridge/` and ai-lib's `lua/` only.
- ai-lib's Lua side keeps one module per `aiLib.<name>` (`lua/<side>/<name>.lua` returns it); a module past the limit splits its parts into `lua/<side>/<name>/<part>.lua` loaded by the module itself through ai-lib's loader.
