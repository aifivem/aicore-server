# Shared packages

`packages/` in the server folder (outside `resources/`, so FXServer never sees it) is its own git repo and is published to npm under `@aicore-fivem`. Resources depend on them with npm ranges; bun links the local copies inside the workspace.

| Package | Content | When |
|---|---|---|
| `@aicore-fivem/lib` | Repeated helpers: `/shared` (anywhere, no natives), `/fivem` (natives on both sides, for `resource/common/`), `/server`, `/client` | A helper is about to be written a second time |
| `@aicore-fivem/shared` | Contracts between resources: types, event/callback names, export types (`CitizenExports`) | Anything one resource uses to talk to another |
| `@aicore-fivem/mysql` | The database engine (`mysql` API, in-process pool, typed `tables<Tables, TableInserts>()`) and the oxmysql-compatible functions `ai-mysql` exports | Every DB access of an ai-* resource |
| `@aicore-fivem/build` | Build steps (`aicore-client-errors`) | Every resource's `build` script |

- The lib replaces ox_lib in ai-* resources (owner decision): never import ox_lib; what is missing gets added to the lib.
- The shared player UI (notification cards, the progress bar and its cancel key, prompts and the interaction key, menus, input dialogs, minigames) is the `ai-lib` resource's own page (`resources/[ai]/ai-lib/resource/ui`, `web/`), not ai-core's: lib `notify` / `progress` / `showPrompt` / `menu` / `input` / `skillCheck` / `lockpick` / `progressFor` / `minigameFor` and the Lua `aiLib` call ai-lib's exports and events (`LIB_UI` in `@aicore-fivem/shared`), and ai-lib runs without ai-core. ai-core keeps what needs its systems: admin panel, character screen, the admin item picker, the keys screen, HUD key hints.
- Resources that do not bundle the lib load it from `ai-lib` like ox_lib: Lua `shared_script '@ai-lib/init.lua'`, JavaScript `@ai-lib/dist/client.js` / `server.js` (`resources/[ai]/ai-lib/CLAUDE.md`). A change to a lib function Lua users have (`AiLib` class in ai-lib's `init.lua`) is made in `ai-lib/lua/` too.
- Every helper is built for scale: benchmark anything that holds or walks a collection at 100k and 1M (`packages/lib/bench/`, `bun run bench`).
- Look in `@aicore-fivem/lib` before writing a helper; add it there when a second user appears. Code specific to one resource stays in that resource.
- Every lib function has a one-line JSDoc saying what it does. `/server`, `/client` and `/fivem` may call natives; `/shared` never does.
- Another resource's export types extend `CitizenExports` in `@aicore-fivem/shared/src/exports.ts` (a type alias per resource, not an interface).
- A change to a package that resources rely on is a `feat:` / `fix:` commit scoped to it (`feat(lib): ...`): release-please releases each package on its own (tags `lib-v1.2.3`) and writes its changelog.

## Actions, players, positions (one line each)

- Action replies: a server handler answers `ActionResult<T>` (`@aicore-fivem/shared`: `{ ok: true, ...T } | { ok: false, error }`) and refuses with `fail("LANG_KEY")` (lib `/shared`); the client runs it with `callAction(name, args, { fallback, timeout?, silent? })` (lib `/client`: resolves the ok reply or null and shows the translated error itself); `replyError(reply, fallback)` / `isActionOk(reply)` read a reply by hand. Never a script's own `fail` / `errorText` / `isObj`.
- Client input readers (`/shared`): `readInt(v, min, max)`, `readFinite(v)`, `readId(v)` (token / net id: positive 32-bit integer), `readText(v, max)` refuse with null (NaN, Infinity, fractions); one-value callbacks take `{ args: oneArg(readId) }`. Never `typeof x === "number"` for a token or net id.
- A minigame a server flow needs (lockpick a door, crack a safe): `await minigameFor(source, { game: "skillCheck" | "lockpick", difficulty?, rounds?, keys?, pins?, picks?, minMs? })` (`/server`) plays it on the player's client and resolves `"won" | "lost" | "broken"` (the last pick broke: take the item); `minMs` is the fastest real play (a skill check stage's green arc starts at 100 degrees: easy 216 deg/s, about 450 ms), a sooner win counts as lost, so give it to any minigame that pays; never a script's own client minigame callback. Lua: `aiLib.minigameFor(source, options)` and `aiLib.progressFor(source, options)` (server, wait in a thread).
- A timed action the server checks (use an item, repair, rob, plant, scrap): `await progressFor(source, { label, duration, anim?, scenario?, face?, allowVehicle?, canCancel?, freeze?, disable?, minRatio? })` (`/server`) runs ai-core's progress bar on the player's client and resolves true only when it ran out there and `minRatio` (0.8) of the time passed on the server; false on cancel, drop, character switch, timeout; a second call for the same player ends the first with false. The start callback checks and answers `{ ok }`, the flow continues after the await and checks distance and stock again; no client progress handler, no finish callback, no token. `label` is a translated text (`Locale` on the server). ai-lib's client answers `LIB_UI.progressForCallback` for every resource.
- A dialog flow checked by the server (a note's text, no timed bar): one module-level `new PendingActions<T>({ minRatio: 0 })` (`/server`): `start(source, data, ms)` gives the token the client sends back, `take(source, token)` answers the data only for the running token (a wrong token never cancels the running one), `peek`, `cancel`; freed on drop.
- Minigames (`/client`): `skillCheck(difficulty | difficulty[], keys?)` (the common FiveM skill check shape: `"easy" | "medium" | "hard"` or `{ areaSize, speedMultiplier }` per stage; resolves true when every stage was hit) and `lockpick({ difficulty?, pins?, picks? })` (`"opened" | "broken" | "cancelled"`; a broken last pick means take the item), drawn by ai-lib (keyboard only, Escape gives up). The answer is the client's word: the server still decides (a chance roll, a `progressFor`, its own checks). Lua: `aiLib.skillCheck` / `aiLib.lockpick` (wait in a thread).
- World objects streamed to the players around them (drops, plants, bodies, placed props): one `new AreaStream<T, View>({ event, view, cellSize?, range?, chunk?, alsoTo?, extra? })` (`/server`, `T` has `id`, `x`, `y`): `set(item, resend?)` / `delete(id)` / `load(items)` (bulk, then every follower's area again), `get`, `values`, `around(x, y, cells?)`, `countAt(x, y)`, `recipients(id)`, `knows(source, id)`; followers `start(source, at?)` (server position), `follow(source, cx, cy)` / `followReported(source, cx, cy)` (a client's reported cell, checked within one cell of the ped), `followAll()` (a timer reading server positions), `stop(source, tell?)`. The client gets `(reset, puts, removes, ...extra)` on `event`: one snapshot, then only changes; who has an item is worked out from the cells, nothing is stored per follower and item. A dropped player's `alsoTo` items are let go (the next player with that id never gets them); the script still updates the item itself. The client half that reports cells is `new AreaFollower(event, cellSize)` (`/client`, `start` / `stop`). Cell math `gridCell(x, y, size)` / `cellKey(cx, cy)` (`/shared`). Never an own cell index, watcher sets or snapshot code.
- A full-screen NUI of a resource (`/client`): one module-level `new NuiScreen<NuiMessage>(name, { cursor?, onClose?, closeCallback? })`: `open(message)` takes the focus (once) and hides the HUDs (`hud.hide(name)`), `close()` gives both back, sends `{ action: "close" }` and runs `onClose` (the script's cleanup), `send(message)` is the typed `SendNUIMessage`, `on(name, parse, handler)` a NUI callback with a parser (null answers `{ ok: false }`, the handler's result or `{ ok: true }` is the reply); the page's `close` callback closes it unless `closeCallback: false`. Never `SetNuiFocus` + `hud.hide` + a `close` callback by hand. Overlays that keep the HUD (chat box, radial wheel, target eye) and ai-core's own shared page keep their focus code.
- Players who get one key's deltas (a lot's cars, an open character): `new KeyWatchers<K>()` (`/server`): `watch(source, key)` (one key per player, replaces the old), `stop`, `of(key)` (set or undefined), `keyOf(source)`; freed on drop, empty sets deleted, every operation O(1) (bench `watchers.bench.ts`).
- Per-player state (`/server`): `new PlayerMap<V>({ onDrop? })` (a Map that empties itself on drop, one shared listener), `new Cooldowns()` (`ready`, `start`, `take(source, ms)`, `left`, `clear`); all module-level. A cooldown that must survive a reconnect is keyed by character id: `new KeyedCooldowns()` (same methods by any key: character id, entity, door id; expired entries swept as the map grows); never an own `Map<charId, deadline>`. Never an own `on("playerDropped")` that deletes from a map. A callback's `lock: true` covers only that callback: two actions that must exclude each other per player (list and sell the same vehicle) share one module-level `new SourceLock()` (`lock.run(source, fail("KEY"), async () => ...)`).
- Who may use a place (`/shared`): the record's own access fields `jobs`, `gangs`, optional `grades` (minimum per name) and `onDuty`, read with `readAccess(record)` into an `AccessRule` (both lists empty = everyone, `isPublic`); the panel spec spreads `ACCESS_FIELDS` into the record's sections and the card takes `accessFields()` (job / gang pickers, on-duty switch, ai-core's generic texts). The server decides with `online.allows(source, rule)`, the client's `canShow` with `allows(rule)`: the same rule, so what a player sees is what the server lets him use. Never a script's own jobs / gangs / grade check.
- Membership checks on the client (`/client`): `hasJob(jobs, minGrade?)`, `inGang(gangs, minGrade?)` (an empty list = everyone), `onDutyIn(jobs)`, `onMembershipChange(fn)` (jobs, duty or gangs changed: `points.refresh()` / a rebuild for blips); a point locked to jobs or gangs shows only to who may use it (`canShow`), the server still checks. Player data (`getPlayerData`) seeds itself from ai-core's `GetPlayerData` on first use, so a restarted resource never seeds by hand.
- Character lifecycle (`/server`): `onCharacter({ loaded(source, character), unloaded(source, charId, reason: "dropped" | "switch") })` also replays the characters loaded before a restart (next tick, from `online`) and covers drops; never `playerLoadedEvent` + replay + drop lines by hand.
- Positions: `Vec3` / `distance(a, b)` / `flatDistance(a, b)` (ground plane) (`/shared`); server `coordsOf(source)`, `entityCoords(entity)`, `isNear(source, point, metres)` (the `near` guard uses it), `vehicleOf(source, { driver? })` (the vehicle the player sits in, only the driver seat with `driver`, 0 on foot); `online.charId(source)` (the loaded character's id or undefined). Client: `playerPed(serverId)` (`cache.ped` for the local player, 0 out of scope), `drivenVehicle()` (`cache.vehicle` in the driver seat, else false), `entityFromNetId(netId, type?)` (the entity now or 0; `waitForEntity` waits), `waypoint()` (`{ x, y }` or null). Lua twins `aiLib.playerPed`, `aiLib.waypoint`. Nearest player: client `nearestPlayer(metres, { from?, filter?(serverId, ped) })` (server id or null), server `nearestPlayerTo(source, metres, filter?)` (scope candidates only).
- Entities from client input (`/server`): `entityFromNet(netId, type?)` (1 ped, 2 vehicle, 3 object), `pedFromNet(netId)`, `vehicleFromNet(netId)` (live entity or 0: checks the id, existence and type), `vehicleNearPlayer(source, netId, { metres = 5, driver? })`; `nearestVehicleTo(source, metres, filter?)`; `nearestVehicleAt(point, metres, filter?)` (a spawn spot is free; walks every vehicle, so rate-limit the action). Never `NetworkGetEntityFromNetworkId` + `DoesEntityExist` + `GetEntityType` by hand.
- Shots: client `onShot((weapon) => ...)` runs in the frame the local ped fires (one per-frame check per resource, only while `cache.weapon` is set); never sampling `IsPedShooting` on a timer.
- Held weapon item: client `inventory.currentWeapon()` (`{ name, label, image? }` or null through ai-core's inventory layer); read it on `onCache("weapon")`, never an inventory's `getCurrentWeapon`.
- `player.teleport({ x, y }, ...)` without `z` (or `ground: "find"`) lands on the lowest ground under x / y that is not inside an MLO / IPL interior (waypoint; each probe height waits for its collision, so a street is not skipped for the roof); `controls.disableAll(reason, except?)` disables every control (groups 0-2) but `except` (noclip, free camera; read them with `IsDisabledControl*`).
- `points.addVehicle(id, { label, icon?, radius?, canShow?(vehicle), onPressed(vehicle) })`: a point on every networked vehicle (the target's global vehicle option or a prompt at the nearest one). `LocalPed` takes a model name or hash and `attach: { entity | () => entity, bone?, offset?, rotation? }` or `seat: { vehicle | () => vehicle, seat }` (not frozen then); its spawn distance is measured from `coords`, so a ped following a moving parent gets a huge `distance` and its own near / bound check (ai-exitsleeping `client/attached.ts`).
- Zone geometry on any side: `ZoneShape`, `zoneContains(shape, x, y, z)`, `zoneBounds`, `polyFromCorners(corners, height)` (a panel `zone` widget's corners as a poly) from `/shared`; client `Zones` uses the same code.
- Panel views: `panel.view(file, read)` (settings: `{ value }` parsed again on each change) and `panel.records(file, readOne)` (records: a `ReadonlyMap` updated per changed record, O(1) per edit) on `AdminPanel` and `AdminWorld`; both update before `onChange` handlers run. `readRecords(raw, readOne)` (`/shared`) for a one-off parse.
- `world.setWeather(type: Weather)`: check a value with `isWeather` (`WEATHERS` / `Weather` / `isWeather` in `@aicore-fivem/shared`); never an own weather list.
- `previewJson(value, max)` (`/shared`): log text of untrusted data built without serializing the rest (the gate and `AdminPanel` use it).

## Periodic work (one scheduler per resource)

- Every periodic job is `every(ms, fn, { active?, name? })` (lib `/fivem`, also `/client` and `/server`): 0 = every frame, 100 = every 100 ms. It returns a `Job` (`set(active)`, `stop()`, `running`); first run one interval after switching on. All jobs of a resource run from one `setTick` that exists only while a job is active; never `setInterval`, `setTick` or a self-rearming `setTimeout` loop for periodic work (a one-off `setTimeout` delay stays).
- A job that runs only sometimes is one module- or class-level `every(..., { active: false })` switched with `set(on)`, not a job created per start; a job that captures per-start values (the vehicle entered) is created on start and `stop()`ped on end. A changed interval is `stop()` + a new `every`.
- A throwing or rejecting job is logged with its `name` (at most once per 10 s per job) and keeps running; the other jobs are not affected. Jobs due in the same frame run in the order they were switched on, grouped by interval; adding or removing jobs inside a job is safe. Lua: `aiLib.every(ms, fn, options)` (one thread per resource sleeping until the next due job; a Lua job never `Wait`s).

## Owned entries, plates, small helpers

- An export provider's entries per calling resource (prompts, hints, radial items, buckets, log channels): `new ByResource<K, V>({ onDrop? })` (`/fivem`, also client / server): `set(key, value, owner = caller())`, `get`, `delete`, `values`, `entries`, `ownerOf`; a stopping resource's entries go (one stop listener, O(its entries)). Reasons that hold a state while any is set (HUD hidden, sync paused): `new Reasons()` (`set(reason, on, owner?)`, `has`, `any`, `onChange`). `caller()` is the calling resource (this one when local); never an own `GetInvokingResource() || ...` fallback or `onResourceStop` cleanup. `ByResource` iterates grouped by owner: a provider whose order across resources is visible (key hints, radial items, connection checks) keeps a Map keyed by `caller()`. Read `caller()` before any `await` (an answer that arrives later is outside the export call). ai-core's own calls into a `Reasons` pass `CORE.resource` as the owner.
- Plates: `plateOf(vehicle)` (`/fivem`, trimmed upper case; throws on a deleted entity: read it before `DeleteEntity` or a store call) and `normalizePlate(text)` (`/shared`) for every plate used as a key or compared; never a raw `GetVehicleNumberPlateText`.
- `formatWeight(grams)` ("750 g", "1.5 kg"), `nearestOf(items, point, pos, max?)`, `randomInt(min, max)` (both included), `pickRandom(list)`, `rollChance(percent)` (`/shared`).
- The server's epoch clock on a client: one `new ServerClock()` (`/shared`): `sync(serverNow)` at each snapshot / start message, `now()` (server time now), `toLocal(serverTime)` (a local `Date.now()` time for countdowns); never an own `offset` field.
- `onStop(fn)` (`/fivem`, also client / server): runs when this resource stops (the side's stop event, one listener per resource); never `on("onResourceStop", (r) => r === ResourceName && ...)`.
- ai-core's job / gang definitions on the server: `definitions.job(name)` / `definitions.gang(name)` (`/server`: each read once from ai-core, forgotten on `CORE.definitionsChangedEvent`); never `GetJobDefinitions()` per call or an own cache.
- A scripted camera: `new ScriptCamera(type?)` (`/client`; `DEFAULT_SCRIPTED_FLY_CAMERA` for hand-held views): `start(at, { pointAt?, rotation?, fov? }, easeMs?)`, `move(at, view, ms?)` (`ms` glides the same camera), `glideTo(at, view, ms)` (a second camera blends in, the old one is destroyed after), `attach(entity, offset)`, `pointAt`, `setFov`, `shake(type, amplitude)`, `blur({ near, far, strength } | null)` (depth of field; its per-frame native runs only while set), `stop(easeMs?)`, `cam`; given back to the game camera when the resource stops. Never `CreateCam` + `RenderScriptCams` + `DestroyCam` by hand (ai-admin's noclip camera is the owner's and stays hand-made).

## Exports of other resources

- One typed handle per resource at the top of the file, never a lookup per call: `const core = resourceExport("ai-core");` then `core.GetCharacter(source)`. The handle is lazy (FiveM resolves each export on first use and forgets it when that resource stops), so it is safe at module level and survives restarts. Never `resourceExport("x").Fn()` inside a function or `const core = () => resourceExport("x")`.
- An optional resource keeps `optionalExport("x")` per call (it answers null while the resource is stopped).

## Interaction points, peds, blips (client)

- Every place a player uses (counter, shop, door, NPC, return spot) is one `Points` entry: `points.add(id, { coords, label, icon?, radius?, height?, targetRadius?, canShow?, onPressed, onEnter?, onExit?, ped?, blip? })` (`height` makes it a cylinder; `targetRadius` sizes the aim spot of a room-sized point in target mode; `promptOnly` keeps a prompt and `preferTarget` a target option (when a target resource runs) whatever the owner picked: seats are `preferTarget`; `world: true | () => PromptAnchor` draws the prompt in the world, tgiann-doorlock style, instead of the right-hand list: a point, or `{ anchors: [{ entity, offset }] }` spots in entity space that ai-lib follows every frame, nearest to the player shown: doors). A target running means one of the target scripts the lib has an adapter for started and answers (`packages/lib/src/client/targets.ts`, Lua `lua/client/targets.lua`, same list and win order: ai-target, tgiann-radialmenu-target, tgiann-target, sleepless_interact, ox_target, qb-target, interact; `docs/compat/target.md`); a new target script is one adapter there, never a script's own target calls. Never hand-made `Zones` + `showPrompt` + `onPromptPressed` + blip code. The point shows as ai-lib's prompt or as a target option (ai-core panel, Interaction; target needs one of those scripts running) and runs the same `onPressed`; an `onPressed` promise blocks the resource's other points until it settles (no own `busy` flag). `canShow` holds the conditions (job, duty, in a vehicle, has a rental); a text that follows a state is a function `label: () => ...` (one point, not one per state); call `points.refresh()` when what they read changes, `points.refresh(id)` when it is one point's state (a robbed target among hundreds) (inside a state bag change handler in a `setTimeout`: the new value is not readable yet). Points (and blips, peds, zones) of a panel records file come from `new RecordObjects(world, file, readOne, (key, record) => { add...; return () => remove... })` (`/shared`; `AdminWorld` or `AdminPanel` as the source; pass the script's own `records` view of the file instead of `readOne` when it keeps one, so an edit is parsed once): an edited record rebuilds only its own objects, a deleted one removes them, `rebuildAll()` only when a setting every record reads changes. Never `points.clear()` + add everything on a panel change. `RecordObjects` builds in its constructor: create it after everything `build` reads (class field order); ids taken from a Set that a rebuild changes are copied before looping. During that first build a class field holding it is not assigned yet: pass the record to `build`, never read the field there.
- A point on world objects of some models (ATMs, vending machines, chairs) is `points.addModel(id, { models, label, icon?, radius?, canShow?: (entity) => ..., onPressed: (entity) => ... })`: a target option on the models, or a prompt near the closest one (the scan runs in ai-lib for every resource, like zones: `AddModelPoint` / `RemoveModelPoint`, the nearest object back on `LIB_UI.modelPointEvent` when it changes; the owner keeps label, `canShow` and `onPressed` and re-reads them every 500 ms only while an object is near; it scans itself (lib `ModelScanner`, 500 ms) only while ai-lib does not run; a point with more than 6 models finds its objects through an object-pool index walked a chunk per scan and kept in a 64 m grid, never one closest-object query per model (bench `modelScan.bench.ts`); object points are skipped while the player is in a vehicle unless `inVehicle: true`, and scans are skipped while the player stands still, refreshed every 3 s). Vehicle models (boats) add `vehicles: true` (the prompt scan walks nearby vehicles; the object scan never finds vehicles). Two states of one object (tie / untie) are two model points with opposite `canShow`, not a label function. Never a script's own `addModel` call.
- `Zones` stays for areas without an interaction (entering a district, a marker that only draws).
- An NPC at a point is the point's `ped: { model, scenario? | anim? }` (a `LocalPed`: created near the player, frozen, invincible, removed when far; targets go on the ped). A ped on its own: `new LocalPed({ model, coords, ... })`.
- Props and held animations (`/client`): `attachProp(model, { ped?, bone, offset?, rotation?, collision?, rotationOrder? })` resolves a local prop held at a ped bone (0 when the model or ped is gone; the caller deletes it, leftovers go when the resource stops); `player.holdAnim(dict, clip, { ...AnimOptions, while? })` keeps an animation playing (put back within 500 ms after a fall or bump, one shared job, one hold per resource) until `stop()` or `while()` answers false. A showroom vehicle is one `new PreviewVehicle()`: `show(model, at, setup?)` (local, frozen, invincible, locked, clean; the latest call wins), `vehicle`, `clear()` (also on resource stop).
- Blips: `blip: { sprite, color, scale, label, route? }` on a point (`route`: a GPS route, `true` in the game's route colour or a colour number) (`label` = the place's map name, not the prompt text; without it the game's default sprite name), or `Blips` (`add(id, opts)`, `remove`, `clear`) / `createBlip(opts)` for blips without a point. The panel's `blip` widget value spreads straight in. Never `AddBlipForCoord` + `BeginTextCommandSetBlipName` by hand.
- The local ped: `cache.ped` / `player` (`player.teleport(to, { heading, ground, fade, keepVehicle })` behind a fade with collision loading, `player.playAnim(dict, clip, opts)`, `player.coords()`), never `PlayerPedId()` outside ai-core's watcher and right after a model change (`cache.ped` lags a model swap up to 100 ms; `player`'s actions read the ped fresh, its reads use the cache).

## State bags

- Every state bag key a resource reads or writes is one module-level instance: `new EntityState("fuel", stateNumber)`, `new PlayerState(PLAYER_BAGS.dead, stateBoolean)`, `new GlobalKey(KEY, parse)`, `new GlobalGroup("door:", stateBoolean)` (keys `<prefix><id>`). Client classes read (`get`, `onChange`); the server classes add `set`. Shared key names live in `@aicore-fivem/shared` (`VEHICLE_BAGS`, `PLAYER_BAGS`) or the resource's `common/`.
- `get` is a memory read (safe in loops and ticks); `onChange((id, value, old) => ...)` sees the new value (no `setTimeout`); entity listeners get the network id (the entity may not exist yet on a client: `waitForEntity(netId)` or resolve on use).
- Parse with `stateNumber` / `stateBoolean` / `stateString` or a `(v) => T | undefined` from the resource's parsers; a removed value is `undefined`, set `undefined` to remove.
- Only the lib touches `Entity().state`, `GlobalState` and `AddStateBagChangeHandler` (and `spawnVehicle`'s bags at creation).

## Vehicles (server)

- A script vehicle is `spawnVehicle({ model, coords, asker | type, plate?, fuel?, keysTo?, purpose?, driver?, seats?, props?, setup?, locked?, bucket?, persistent?, bags? })`: server creation, orphan mode, plate, fuel (through the fuel layer), state bags, keys, the look (`props` = stored VehicleProps, `setup` = fresh-vehicle extras: `maxed`, colours, livery, tint, dirt, `engineOn`; `colors` (GTA colour indexes); ai-core applies both on the owner client), doors locked, routing bucket, and the driver and passengers seated (retried until they sit) in one call; null when the model does not exist or creation failed. A vehicle always gets a plate (a random one when none is given) and the keys wait (up to 3 s) until the server reads that plate: before the owner client's first sync the server reads an empty plate. `asker` is a player whose client tells the spawn type (ai-core's client answers `CORE.vehicleTypeCallback` for every resource; an answer serves only that player until a second player's client gives the same, then it is kept for the model); never a per-script `vehicleType` callback. `vehicleType(model, asker)` checks a model before charging money.
- Keys always name their purpose (`KeyPurpose`): `purchase` (bought, a new key), `garage` (owned vehicle out of storage), `job` (work vehicle), `rental`, `temporary` (default: admin spawn, test drive, robbery). Key systems like tgiann-hotwire behave differently per purpose.

## Items

- Every item call goes through lib `inventory` (server `addItem`, `removeItem`, `getItemCount`, `hasItem`, `canCarryItem`, `getItems`, `clearInventory`, `registerStash`, `openInventory`, `registerUsableItem`, `getItemDefinition`, `registerShop(name, label, [{ name, price }])` once at start, `openShop(source, name)` after the script's own checks; client `openInventory`, `hasItem`), never an inventory's own exports: ai-core forwards to the active inventory (`docs/compat/inventory.md`).
- Register usable items and stashes once at the script's start; ai-core keeps them for inventories that start later or restart, so no `onServerResourceStart` re-registration.
- Vehicle keys go through lib `vehicleKeys` (server), never a key script's own exports (ai-vehiclekeys included); ai-core forwards to the active key system (`docs/compat/vehicle-keys.md`).
- Item effects (hunger, thirst, stress) arrive on ai-core's `CORE.itemUsedEvent`, not an inventory's own event.
- A player's death: listen to ai-core's server event `CORE.playerDiedEvent (src, killer, weaponHash)` (FXServer's `onPedDeath`; ai-core requires FXServer 38039+); never poll health.

## Commands and keybinds

- Every server command is `addCommand(name | [name, ...aliases], { help, params, restricted }, (source, args, raw) => ...)` from `@aicore-fivem/lib/server`, never a bare `RegisterCommand`. `help` and param `help` are lang texts.
- `params`: `{ name, type: "number" | "playerId" | "string" | "longString", help?, optional? }` in order (`longString` last, takes the rest of the line). They are parsed before the handler runs; wrong input shows the error and the usage line as an ai-core notification (ai-core's `COMMAND_*` texts). `args` is typed from them (`args.id` is `number`, `number | undefined` when optional). `source` 0 = server console. A param object shared by several commands is declared `as const`, or its name and type widen and `args` loses them.
- `restricted`: `false` (default, everyone), `true` (ai-core admins, ACE `ai.admin`), or an ace / principal or a list (`"group.admin"`, `["ai.admin", "ai.job.police"]`). Checked on the server with ACE; `command.<name>` always allows too (server.cfg, txAdmin); ai-core grants `command.<name>` to listed principals (needs `add_ace resource.ai-core command.add_ace allow` and `command.remove_ace` in `permission.cfg`). Never check permissions by hand inside a handler.
- Chat suggestions (with help and params) go only to players allowed to use the command, refreshed on character load and job or gang changes; ai-core's panel lists every command (Commands tab).
- `new Keybind({ name, description, defaultKey, defaultMapper, hint?, icon?, hintLabel?, onPressed, onReleased })` (client): `hint: "foot" | "vehicle" | "always"` lists the key on the HUD's key hints in that situation (the owner can override or hide it per keybind in the panel), `icon` is the Font Awesome name drawn next to it, `hintLabel` the short hint text (one or two words; the description is for GTA's key settings); `currentKey` is the key the player has bound now (GTA's icon-coded keys such as F1-F12 and Tab give the registered key); `name` is a stable id without the key (`inventory_open`); the lib registers the mapping `+<name>_<key>` with the key ai-core's panel sets (Keybinds tab), else `defaultKey`. Registration waits for ai-core's answer (one round trip at start). A panel change applies at once: the new key gets its own mapping (FiveM keeps old mappings and the player's binding per command, so the key is part of the name) and the old one stops acting. Another resource that needs a keybind's bound key asks ai-core's client export `GetKeybindKey(name)` (the mapping command is `+<name>_<key>`).
- lib `menu` item icons are looked up in ai-lib's icon map (`resources/[ai]/ai-lib/web/src/lib/icons.ts`); a name missing there shows a dot, so add it there first. The admin panel's icons are ai-core's own map (`web/src/features/admin/icons.ts`).
